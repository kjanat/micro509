Sign and verify JWTs ​

Use micro509/jose to sign JWTs with RS256 and verify their signatures, issuer, audience and expiry. Verification accepts a public CryptoKey, a local JWK Set (JWKS), or a resolver that fetches an issuer's JWKS.

A JWT carries JSON claims. Its JWS signature covers the encoded header and claims. A JWKS is a JSON document of public keys, usually identified by a kid. Successful verification returns the authenticated claims for your application to use in its authorization decisions.

Choose your verification inputs ​

Supply these values from your application's configuration:

InputExamplePurpose
Allowed algorithms['RS256']Restricts the accepted signature algorithm.
Issuerhttps://issuer.exampleIdentifies the issuer you expect.
Audienceapi://ordersIdentifies the application the token is intended for.
Token type'JWT' or 'at+jwt'Selects the token profile accepted by this application.
Key sourcePublic key, local JWKS, or configured JWKS URLSupplies the key trusted to verify that issuer's signature.

The token's alg, iss and key-location headers do not choose these settings. Use the token profile specified by your issuer. Distinct token uses may need separate types, audiences and claim policies even when they share signing keys.

Verify the same JWT three ways ​

This runnable example signs one demo token, prints the token and public JWKS, and verifies it with each key source. The header's kid: 'demo-1' selects the matching entry in the JWKS. All three paths apply the same issuer, audience, token type and expiry checks.

For the remote-resolver path, a small custom transport serves the demo JWKS as an HTTP Response in memory. This makes the complete example runnable here without an external issuer. The resolver still performs key selection, caching and real signature verification. Connecting to your issuer explains how to use its HTTPS endpoint.

ts
import { generateKeyPair } from 'micro509/keys';
import {
  createJwksKeyResolver,
  createRemoteJwksKeyResolver,
  parseJwks,
  signJwt,
  verifyJwt,
} from 'micro509/jose';

const keys = await generateKeyPair({ kind: 'rsa' });
const issuer = 'https://issuer.example';
const audience = 'api://orders';
const now = Math.floor(Date.now() / 1000);
const token = await signJwt({
  privateKey: keys.privateKey,
  algorithm: 'RS256',
  header: { kid: 'demo-1' },
  claims: { iss: issuer, aud: audience, sub: 'demo-user', exp: now + 300 },
});
const publicJwks = {
  keys: [
    {
      ...(await keys.exportPublicJwk()),
      kid: 'demo-1',
      use: 'sig',
      alg: 'RS256',
    },
  ],
};
console.log('JWT:', token);
console.log('Public JWKS:\n' + JSON.stringify(publicJwks, null, 2));

const parsed = parseJwks(JSON.stringify(publicJwks));
if (!parsed.ok) throw new Error(parsed.code);
const local = createJwksKeyResolver(parsed.value);
let requests = 0;
const remote = createRemoteJwksKeyResolver({
  url: `${issuer}/.well-known/jwks.json`,
  // Demo transport. Omit this property to fetch a real issuer's HTTPS URL.
  transport: async (url) => {
    requests++;
    console.log('JWKS request:', url);
    return new Response(JSON.stringify(publicJwks), {
      headers: {
        'content-type': 'application/json',
        'cache-control': 'max-age=300',
      },
    });
  },
});

const policy = {
  algorithms: ['RS256'],
  tokenType: 'JWT',
  claims: { issuer, audience },
} as const;
for (const [label, key] of [
  ['Direct key', keys.publicKey],
  ['Local JWKS', local],
  ['Remote JWKS', remote],
] as const) {
  const result = await verifyJwt(token, { ...policy, key });
  console.log(label, result);
  if (!result.ok) throw new Error(`${label}: ${result.code}`);
  console.log(`${label} claims:`, result.value.claims);
}

// Reuse the resolver for subsequent requests to use its cached JWKS.
console.log(
  'Cached verification:',
  await verifyJwt(token, { ...policy, key: remote }),
);
console.log('JWKS requests after two remote verifications:', requests);

// A valid signature does not make this token valid for a different audience.
const rejected = await verifyJwt(token, {
  ...policy,
  key: remote,
  claims: { issuer, audience: 'api://another-service' },
});
console.log('Wrong audience (expected audience_mismatch):', rejected);

The three successful results should contain the same sub, iss, aud and exp claims. Two verifications through the remote resolver should make one JWKS request. The final result should be audience_mismatch, despite using the same token and signing key.

result.value.claims contains all claims. result.value.registered contains the validated registered claims, and result.value.header contains the protected header. decodeJwtUnverified only reads a token's contents. Use verifyJwt before acting on those claims.

Connect to your issuer ​

Configure one createRemoteJwksKeyResolver per issuer at application startup. Use the issuer's documented JWKS URL and omit the demo's transport property. The resolver uses fetch. Pass the received compact JWT string to verifyJwt with that resolver as key, as in the example above.

For an HTTP API, obtain the token from the request's Authorization: Bearer … header. Your issuer and audience come from configuration. Reuse the resolver across requests so its key cache and refresh cooldown can work.

SituationResolver behavior
First verificationFetches the JWKS when verification reaches key resolution.
Another request within freshness lifetimeUses the cached set.
Unknown kidAttempts a refresh if the cooldown permits it. Otherwise returns key_not_found.
Expired cached setRequires a refresh. If it cannot fetch a fresh set, returns jwks_unavailable.
Key rotationA refresh replaces the set. Publish a new key with a new kid.

The default fetch deadline is 5 seconds, response limit is 64 KiB, key limit is 32, and refresh cooldown is 30 seconds. The cooldown suppresses new fetches, so a request can fail during that interval. It does not wait for a scheduled retry. Pass signal: AbortSignal.timeout(10_000) to verifyJwt to bound how long a particular caller waits.

HTTP caching, redirects and custom transports

Freshness follows Cache-Control: max-age, then Expires, then defaultTtlMs (10 minutes). Response age is subtracted and the result is capped at maxTtlMs (24 hours). A no-store or no-cache response serves the verification that fetched it and supplies no fresh cached set for later calls. An expired set is never used after a failed refresh.

Fetches use cache: 'no-store' so the resolver's refresh reaches the issuer even when a browser HTTP cache would consider its response fresh. Custom transports must honor that mode. Concurrent callers share one fetch. Cancelling the last waiter aborts it.

URLs must use HTTPS, or HTTP on loopback. Redirects are refused by default. Explicitly allowed redirects must satisfy the scheme and destination policy. Browsers hide manual redirect targets, so they cannot follow this redirect path. Configured headers are sent only to the original origin. Use transport for proxies or network egress rules, including DNS/address restrictions.

See RemoteJwksConfig for the full configuration surface.

Handle rejected tokens ​

A JOSE verification failure has result.code at the top level: { ok: false, code, message, details? }. The examples print that result so you can inspect the code and details. In an application, handle the relevant category:

CodesApplication response
expired, not_yet_valid, issued_in_future, token_too_oldReject the token under the configured time policy.
issuer_mismatch, audience_mismatch, token_type_mismatchReject a token for a different issuer, application or token profile.
invalid_signature, malformed-token codesReject the token.
key_not_found, key_unsuitable, ambiguous_keyCheck the issuer's key publication and your key-selection configuration.
jwks_unavailable, jwks_malformed, abortedHandle the key-source failure or cancellation. Verification has not succeeded.
invalid_optionsFix your application's verification settings.

Use JOSE error codes for the complete list. Signing and resolver construction throw a ResultError for invalid configuration.

Adjust claims policy ​

exp is required by default. Present exp, nbf and iat values must be JSON numbers. Expiry is reached when the verification time is at or after exp.

Option in claimsDefault and use
issuer, audienceRequired. Accept a configured string or list of strings.
requiredClaims['exp']. Add claims your token profile requires. Supplying a list replaces this default.
clockToleranceSeconds0. Accepts 0–600 seconds for time checks.
maxAgeSecondsOmitted. When supplied, also requires iat.
futureIssuedAt'reject'. Use 'allow' only when your token profile permits it.
nowCurrent time. Supply a function returning a valid Date for a controlled verification time.

The API also exposes { unchecked: true } for issuer, audience and token-type policies when an application deliberately delegates those checks. The examples use explicit expected values. tokenType: { absent: true } requires the typ header to be absent.

Sign and verify raw JWS data ​

Use compact JWS for a signed byte payload. This separate API verifies the signature and header policy. It does not apply JWT claim checks to the payload.

ts
import { generateKeyPair } from 'micro509/keys';
import { signCompactJws, verifyCompactJws } from 'micro509/jose';

const keys = await generateKeyPair({ kind: 'rsa' });
const token = await signCompactJws({
  privateKey: keys.privateKey,
  algorithm: 'RS256',
  payload: new TextEncoder().encode('Order 42: ready to ship'),
});
const result = await verifyCompactJws(token, {
  algorithms: ['RS256'],
  key: keys.publicKey,
  tokenType: { absent: true },
});
console.log('Compact JWS:', token);
console.log('Verification:', result);
if (result.ok)
  console.log('Payload:', new TextDecoder().decode(result.value.payload));

Supported formats ​

The module implements compact JWS and JWT with RS256 and RSA keys of at least 2048 bits. JWE, JSON JWS serialization, nested JWTs, detached or unencoded payloads, critical-header extensions and other signature algorithms are unsupported. Parsing checks canonical base64url, UTF-8, duplicate JSON members and size/depth limits. Configure these bounds through JoseLimits.
